Living PRD (Product Requirements Document)

Updated every week as we test with real users and learn what works. PRD v3, updated Nov 22, 2026 (Build 3): added hosting, data and security choices.

1. Target User & The Job to Be Done

Who is this for? Me and my NYU Stern MBA classmates preparing for automated one-way video interviews (e.g., HireVue), where answers have to be short and fit a strict time limit.

The painful "Before" workflow: Manually edit and cut down word count, which can often be slow and clunky

The "After" workflow with this product: Provide your question, resume, and speaking speed and get a precisely tailored answer.

2. Scope & Explicit Non-Goals

  • In Scope (Core Workflow): Convert broad resume text into specific answers.
  • Out of Scope #1: Self-editing or spell check
  • Out of Scope #2: Making specific genre toggles (i.e. for a speech/short answer question/etc)
  • Out of Scope #3: Setting a specific word target

3. How It Works Under the Hood & Riskiest Assumption (Week 2+)

Riskiest Assumption: HireVue and other automated interview software often checks for active AI software in other tabs.

Simple Architecture: User sends question and resume text and speaking speed to server, server sends to AI through call, AI produces output, which is returned to the user

Live setup (Build 3): Browser → Node.js server on Render → Claude Haiku 5.5 (Anthropic API) → server counts the words and checks the 60-second budget → answer back to the browser. The API key lives only on the server.

4. Hosting, Data & Security Choices (Build 3)

  • Hosting: Render (free Web Service). The app is a small Node.js server, and Render runs that directly and redeploys automatically whenever main changes. GitHub Pages only hosts static pages and can't keep the API key secret. Trade-off: the free server sleeps after about 15 minutes idle, so the first visit can take up to a minute.
  • Database: none, on purpose. The app saves nothing. Questions and resumes are used for one answer and then dropped, so there's no user data to leak and no sign-in to build. If we later add saved answers or accounts, we'd add a real database (Supabase or Neon) with Row Level Security.
  • Security choices:
    • API key: kept only in Render's environment settings, never in the page or the repo.
    • Rate limits: 10 answers per visitor every 15 minutes, plus 60 per hour across the whole site. The audit found that the first version could be bypassed with a faked header; that was fixed and retested live.
    • Spending caps: $1 per day in the app and $8 per month on the Anthropic account.
    • Untrusted input: input size limits; the resume is treated as data, not instructions; AI output is shown as plain text.
    • Browser: security headers block framing and file-type guessing.
    Full audit, attack log and remaining issues: SECURITY.md.
  • Analytics: PostHog on the live site. It records pageviews, clicks, session replay and funnel events (answer_requested → answer_generated → answer_copied). Events never include question, resume or answer text, and the answer box is hidden in replays.
